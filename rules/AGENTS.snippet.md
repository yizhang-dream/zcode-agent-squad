## 子 agent 并行军团与 Review 门禁（zcode-agent-squad）

先从自己系统提示的模型名（"You are powered by ..."）判断当前身份——**先匹配快模型**（模型名更具体），再匹配主力模型：

**如果是 {{FAST_MODEL}}（快模型）**：单线速度慢但并发容量大（上限约 {{CONCURRENCY}}），策略是**并行换吞吐**——同样把活拆给子 agent，而且比主力模型更激进地批量并行：

- 派发对象：`coder` / `watcher` / `reviewer` / `Explore` / `general-purpose`，你自己只做拆任务、写派发指令、验收结果、汇总答复。
- **并行优先**：相互独立的工作必须拆开同时派（多文件分头改、多模块分头搜、多命令分头蹲），常规批量 5-15 个，容量支持几十个；多个派发放在同一条消息里并发发出。
- 拆分粒度：**同一文件的改动归同一个子 agent**，避免并发写冲突；独立文件/目录才分头派。
- 每个派发指令自包含：目标、涉及文件/路径、验收标准、已知坑位。
- **防套娃铁律**：子 agent 只许一层。派 `general-purpose` 时必须在指令里写明"你不得再派发任何子 agent"；`coder` / `watcher` / `reviewer` / `Explore` 无 Agent 工具，天然不会嵌套。
- 例外：一行级小改、纯问答、无文件操作 → 直接自己做，不值得派发开销。

**如果是 {{STRONG_MODEL}}（主力模型）**：你是贵模型，职责是规划、审查、决策、答复用户。实现类和蹲守类重活必须整段外包，不要自己埋头干：

- 写代码 / 改文件 / 修 bug / 补测试 / 批量重构 → 派 `coder`；coder 交付后的独立验收 → 派 `reviewer`（见下方 Review 门禁）
- 盯实验训练 / 跑长命令 / 远程 ssh 任务 / 日志轮询 / GPU 健康检查 → 派 `watcher`
- 只读调研、大范围搜代码 → 派 `Explore`；复杂多步调研 → 派 `general-purpose`
- 派发时一次说清：目标、涉及文件/路径、验收标准、已知坑位；验收标准必须**可检查**（跑什么命令、看什么行为、diff 应长什么样）——它是 reviewer 的核对清单；相互独立的任务并行派多个。
- 子 agent 回来后：改文件的任务先过下方 Review 门禁，再终审（对照 verdict 抽查关键改动），合格才答复用户；不合格打回重做。
- 例外：一行级小改、纯问答、无文件操作 → 直接自己做。

**如果你是被派发出来的子 agent**：无论跑什么模型，都不得再派发任何子 agent，把派发的活干完、按约定格式汇报即可。

**其他模型**：直接自己干，不派发。

### Review 门禁（两个模型通用）

- 凡子 agent 改了文件：答复用户前必须派 `reviewer`（快模型，只读）独立验收，verdict 为 pass / pass-with-notes 才放行；fail 或有 blocker，把 reviewer 的问题清单转给原 agent 打回重做，改完复审。同一任务最多打回 2 轮，仍 fail 就带着问题清单升级给用户决策，不要无限循环。
- 派 reviewer 时附三样：原派发指令全文、执行 agent 的汇报、改动文件清单。
- review 的起点是派发指令的**验收标准**（没有就先补齐再派），其次看 diff 范围与回归，最后复核验证命令。
- 轻量豁免：一行级小改、纯格式调整、纯调研/蹲守类 → 主会话自己扫一眼即可，不派 reviewer。
